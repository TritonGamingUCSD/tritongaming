# Features reference

Who may do what is in [roles-and-capabilities.md](roles-and-capabilities.md).

How the main pieces work and where the code is. Each section names the files so you can start reading in the right place.

## Meetings (live screen)

Code: `src/app/(portal)/portal/meetings`, `src/app/api/meetings`, `src/lib/meetings`.

- The projector screen (`api/meetings/[id]/live`) refreshes when the server sends a signal (`notifyMeetingLive`, called after a check-in, answer, reaction or excuse) and every 30 seconds as a backstop. Only reactions newer than a cursor are returned; totals come every eighth refresh.
- People answering a poll or rating watch the results move the same way.
- The availability grid blocks times a person already has: meetings meant for them or hosted by them and events they have a ticket for (`lib/meetings/busyItems.ts`).

## Teams (TG Members → Team)

Code: `TeamsPanel` in `src/app/(portal)/portal/meetings/MeetingsSectionContent.tsx`, `src/app/api/meetings/groups`, table `meeting_groups`.

- A team is a name and a list of people (`meeting_groups.member_ids`). It is also what a meeting, plan or event can be sent to, so there is one list, not two.
- **By team** lists the teams closed (name and size only); “Show who” opens one to reveal its people as removable chips, with an “Add person” box. Searching opens the teams a person is in; **By person** shows each officer, lead and exec with their teams, a “no team yet” filter, and a “+ Add to a team” picker. The view is in the address (`/portal/members/team/people`).
- Changes use the same update route as the editor, so people added to a team are told about the meetings and plans the team was chosen for (`lib/meetings/groupChanges.ts`).
- Each person's teams are loaded with the roster (`getMembersData`) and shown as chips on their TG Members card (`MemberCardBody`, `teams`). The public Team page never passes them.

## Documentation

Code: `src/app/(portal)/portal/docs`, `src/app/api/docs`, `src/lib/docs`.

- Open pages refresh on a `notifyDocs` signal (publish, move, rename, delete) with a 2-minute backstop.
- Pages are grouped in categories (each with a color) and can have sub-pages. Edits go to a draft; **Publish** makes them live and keeps a version. A new page starts from one short how-to outline; there are no templates.
- **Layout:** the doc tree is always on the left (a drawer on a phone) and the search box sits above the content. Search (also `/`) matches titles, tags and text, marks the matching words and shows the line around the match.
- **Home, in order:** Quick links, docs for your own teams, Start here (pinned; editors drag to reorder), How-to guides by category, then favorites and recently updated. A banner lists required reading you haven't opened.
- **Quick links** are not documents. Each is a title, an https address, a one-line note and optional teams, kept in `quick_links` and managed on the home with **Add quick link** and the pencil on a tile (editors only: `manage_docs`). They have no tree, drafts, versions, comments or counts; they appear in portal search. Editors drag tiles to change their order (readers see links for their own teams first, then that order). The same tiles also appear on the portal dashboard for anyone who can read the docs.
- **Last reviewed:** each page shows when it was updated and when an editor last marked it as still correct (⋯ → Mark as reviewed, stored in `docs.reviewed_at`). A review counts like an edit for the six-month "worth a look" warning.
- **Organizing:** leads, exec and admins (`manage_docs`) organize in the tree itself. Drag a doc to reorder it or drop it on a category to move it; drag a category header to reorder categories. A category's ⋯ menu has Rename, Change Colour, Add Doc Here and Delete, and **New Category** is at the bottom of the tree. Officers and others only read.
- **Files and history:** a file is attached inside the text, where it belongs: **Insert, File**, `/file`, or drop or paste any file into the editor (pictures show in place, other files become a 📎 link). There is no separate attachments list. **History** opens the published versions on the right and shows the chosen one in the main area with what changed since the version before it marked (new text green, removed text red and struck through); **Restore This Version** brings it back as the draft.
- **Teams:** an editor picks which teams a page is useful for (Team tab in TG Members, stored in `docs.teams`). People on those teams see it under "For your team".
- **Editor:** Tiptap, saved as Markdown. Text colour and highlight use a fixed palette and are stored as inline `<span data-c>` and `<mark data-h>`; the reader renders them through `remarkDocColors`.
- **Required reading:** editors choose roles in a page's ⋯ menu (`doc_required_roles`). Opening the page counts as read (`api/docs/read`, `doc_reads`). Editors see who has read it, can remind the unread (once a day) and can **ask everyone to re-read** after a big change (clears the marks and sends one bell).
- **Comments:** always open under each published page (`doc_comments`). The page's author and last editor get a bell; editors can resolve or delete.
- **Report a problem:** ⋯ → "Report a problem with this doc" opens a Help ticket in the **Doc problem** category with a link to the page.

## Help and role requests

Code: `src/app/(portal)/portal/help`, `src/app/api/help`, `src/lib/notifications/help*.ts`.

- Anyone can open a ticket; exec and admin see all of them.
- **Role requests:** "I need a role" opens a short form (role, division, who can vouch). It becomes a ticket whose text `parseRoleRequest` can read back. Admins (only) see **Approve and give role** on it, preselected from the request. Approving gives the role (`withRole`), replies on the ticket, notifies the person, resolves the ticket and writes the audit log.

## Trivia (quiz games for events)

A portal section (Events group). **Everyone signed in can play**; officers and above (`host_trivia`) write quizzes, host games and see results.

- **Quizzes:** a quiz owns a *pool* of multiple-choice questions (four answers, one right, an optional category). The quiz page has two tabs, **Questions** and **History** (the games it has had). Questions is grouped by category (collapsible sections with counts, questions without a category first under “Needs a category”, a filter box across all of them, totals shown above the table; the order of questions does not matter, so rows are not numbered), as a table that stays locked until **Edit Questions** is pressed (so nothing changes by accident), then edited in place (click a cell; a round button beside each answer marks the right one, shown in green; **Done Editing** locks it again) with **Add Question** (a form), **Paste Many** (pasted text or a CSV file, read and checked before anything is added) and **Export CSV** (columns category, question, A to D, answer: the same ones Paste Many reads). A quiz says how many questions a game asks (copied to the game when it is opened, fixed in the lobby).
- **Time:** always automatic and never edited: 30 seconds to look up, read and tap plus a second per word over the question and the four answers, to the next 5 s, between 40 and 120 (`suggestSecs` in `lib/trivia/game.ts`, worked out when a game is drawn; the `secs` column is kept in step on every save but is not shown).
- **Choosing any picture** (profile photo, a question's picture, an emoji, a QR icon, help screenshots, event images) always goes through `components/ui/PictureDialog`: click the picture's box, then drop or choose a file, press **Paste Picture** or Ctrl/Cmd+V (only while the popup is open, so a paste can never land by accident), see a preview, and press **Use This Picture**; **Remove Current** is there when one exists. Dropping or pasting on the page itself does nothing. `useFileDrop` is only for non-picture files (fonts).
- **Pictures:** a question can have one optional picture, shown with the question on the host's big screen only (never sent to phones). The browser shrinks it to a WebP of about 120 KB at most (the server takes 250 KB at most; the `trivia-images` bucket refuses anything but WebP over 256 KB) and uploads it through `api/trivia/quizzes/<quiz>/image`; the address is kept in `trivia_questions.image` (and in a game's `plan`) so the weekly storage tidy-up sees it as in use. Replacing, removing or deleting the question removes the file.
- **Auto-advance:** after the answer has been on screen for 6 seconds (`AUTO_NEXT_SECS`) with no button pressed, the host screen moves on by itself: to the next question, or after the last one to the results (the button reads "Show Podium · 6" and counts down; the host can press it early). Every question with a category shows its 3-second category card, also when it is the same category as the one before.
- **Look and motion:** a game starts with a 3-2-1-GO countdown (4 s, `COUNTDOWN_MS`) on the host screen and the phones, then each question's category card, then a thin line that sweeps along the top bar while the question text fades in (nothing covers the screen); waiting and loading screens use a bouncing-shapes mark; the last 5 seconds pulse, wrong answers shake out and the right one pops and glows on reveal. All motion stops when the device asks for reduced motion. A game screen never scrolls: the body is clipped under the top bar and shrunk to fit the window (`FitBox`, down to 40%), on the host screen and on phones.
- **Categories:** every question needs a category (typed; a different capitalisation takes the spelling the quiz already uses). Every question opens on a full-screen category card for 3 seconds on the host screen and the phones; the question and its clock start after it (the clock begins at `q_started_at`, and an answer sent before it is refused). A question with no category counts as unfinished (marked “Needs a category”, never drawn), the same as one missing an answer. Drawing stays fully random; a category is only a label and a card.
- **Settings of a quiz:** questions per game; **Top 3 can't play this quiz again** (on by default); **Only certain officers can open this quiz**.
- **Private quizzes:** with that switched on only the quiz's creator, Admins and the people ticked on its list (officers and above) can open it, edit it, host it and see its games and results. Everyone else who can host sees its name with a lock and nothing else (it is left out of the Live list and games lists). Only the creator or an Admin sees and changes the list. Players are not affected: anyone with a game's code can still play it.
- **Hosting:** Host Game (one button; a quiz that already has a lobby open opens that lobby again, lobbies left unused for 6 hours are cleared) opens a lobby with a TG-styled QR code and a 6-digit code (older 6-character codes still work). A fresh random set is drawn when the game starts, questions earlier games of the quiz did not use first; the order of the answers is shuffled. The host screen shows the clock, a bar of how many have answered (built for 30 to 100 players: a player list with search and a compact layout when there are many), then the right answer, how many chose what and the top five; the question closes by itself when time is up or everybody answered, and the host clicks Next. Ends with a podium revealed 3rd, 2nd, then the winner (with confetti; each place has a medal, a crown for the winner, an initial badge and the name on a taped plate), then places 4 to 10 and a few facts (fastest right answer, longest streak, toughest and easiest question, overall accuracy), and a New Game button that opens a fresh lobby of the same quiz.
- **Playing:** open the QR code, or Trivia → Play and type the 6 digits. Names are portal display names. Phones show only four big coloured shape buttons (no letters, like Kahoot; the big screen shows the same shapes beside the answers): the question and the words of the answers are on the big screen, so a player has to see it; an answer cannot be changed once tapped (the first one counts). After the reveal they show right or wrong, the points, the streak, the rank, and their answer next to the right one. Scoring is 500 to 1000 points per right answer (faster is more); ties are split by total time on right answers. Players can rejoin or join late; the host can remove someone and let them back in (hold to confirm).
- **Guests:** a quiz can be **Open to guests** (a setting, off by default). Its games then show a QR code to the public page `/play/<code>` (also `/play`, type the code), where anyone without an account picks a nickname and plays. A guest signs in anonymously (Supabase anonymous sign-ins; no profile row, nothing in the members list). Guests may only reach the Trivia join and play routes (everything else answers 401 in `proxy.ts`, and the database refuses them on every table and bucket, see database.md). A game of a quiz that is not open to guests answers a guest with "sign in to play". The same nickname twice in a game gets a number. Guests are never held back by the Top 3 rule. A person signed in with an account who opens `/play` is sent to the portal's Trivia and plays as themselves. Supabase limits anonymous sign-ins per network address (about 30 an hour by default): raise it under Authentication → Rate Limits before a big event, and consider enabling captcha.
- **Top 3 rule (a setting of the quiz):** when on, the top three of a game cannot join a later game of the same quiz (they show on the host's list as "not in", and the host can let them in). Off: nobody is held back and no winners are recorded. Deleting a game frees its top three.
- **History:** every game is kept (running ones too). The quiz's **History** tab lists them 20 at a time with Load More Games, with results and delete; each quiz card shows how many times it has been played and when last, with a History button; a Live now strip on the quiz list shows running games and lets a lobby be closed. Players see only the games they joined (Play → Your Games).
- **Live:** the server sends small messages on a Supabase Realtime channel (`trivia:<game id>`; the host alone also gets `trivia-host:<game id>` for joins and the answered count); screens also ask every 10 seconds and when a phone wakes up. The server decides the clock, the points and the right answer (never sent before the reveal).
- Tabs: Play (first, where Trivia opens) and Quizzes (officers and above). Addresses: `/portal/trivia/{play[/<code>] | quizzes[/<quiz>[/history[/<code>]]] | host/<code>}`. A whole quiz card opens the quiz.

## Event Logistics (requests, allocation, event day, inventory, tools)

A self-contained portal section (Team group). **Every recruit, officer and above can look**; only people with the Event Logistics permission (exec, admin, or granted) change anything. The work runs in three steps: **Requests** (what each team needs) → **Allocation** (which device or prize goes to which request) → **Event Day** (tick what happens).

- **Addresses (the event first):** `/portal/logistics` is the list of events; `/portal/logistics/<event>` its requests; `<event>/requests[/prizes]`, `<event>/loaners/sponsor|officer`, `<event>/prizing`, `<event>/devices[/event-day|/planning][?view=type,open]`; `stock/prizes` and `stock/devices` with no event; bare `/prizing` and `/devices` open on today's (or the next) event. The tabs on top are **Devices | Prizing | Events**. Every older address (page first like `prizing/<event>`, `requests-devices`, `allocation-…`, `event-day-…`, `inventory`, `equipment`, `tools/…`) still opens the right place (no redirect, tidied in place).
- **Search:** the search on the Devices and Prizing pages finds any device (by ID, name or type) and any prize (by name, type, sponsor or size), says where it is in this event and how many are left, and jumps to it. `<event>/requests[/prizes]` and `<event>/loaners/...` open that part of the event's page (folded parts open and scroll into view).
- **Requests are the source.** A device request (a bundle or a device type, how many, which games, a team, one contact, notes; the contact is one person, a division lead or an officer or above, the asker by default) makes the empty rows under its team in the Devices allocation (a bundle makes a set per unit). Editing the request adds or removes rows (empty ones first; a device with an event-day step done is never taken out); editing a bundle follows into every open request that uses it (parts added or removed, renames carried); a bundle that a request asks for can't be deleted. A prize request makes a **pool** for its team with a target (how many, dollars) and trims the pool's prizes when it shrinks. The request's contact is written onto its team, so every page shows the same one. No written answers: logistics tells people in person.
- **Devices allocation:** each row is what was asked for, with an ID box: typing an ID fills an empty row or swaps the device (inventory devices, sponsor loaners and officer loaners are all accepted; IDs are suggested), clearing it empties the row. Rows can't be added or deleted here, only in the request; a device no request asked for is flagged. Grouped by team or by device type; Collapse all also folds bundles; a list of devices still free sits under the teams.
- **Who may do what:** once a request is sent only the Event Logistics team can change or remove it (including who the contact is); swaps are Event Logistics only; any officer can tick or untick steps, and each tick records who did it (shown on hover).
- **Event day:** only ticking, typing an ID to mark (IDs are suggested from the allocation), and swapping; nothing structural changes. The page asks a tiny question every 20 seconds while visible (requests every 30) so several people on one event see each other's work; saving the same request at once leaves exactly what it asks for. A tick shows at once (spinning ring while it saves), an Undo bar follows it, and a tick made while offline waits on the device and is sent when the connection returns. A camera button scans a device's QR (its ID, or a link ending in it) to mark the selected step; "Unfinished Only" hides lines that are done (`?view=open`).
- **Devices** and the lists of sponsor loaners and officer loaners are edited **in place**: plain text until clicked, saved when you leave the box; a Details pop-up holds the rare fields. Forms that remain are pop-ups (an existing item's pop-up holds only what its table row has no box for; on a phone every pop-up is a full-screen sheet with its buttons pinned); Add Device asks only ID, Type, Shelf and Tier (More Details for the rest). Colours mean something: red = needs a device or is wrong, amber = to check, green = ready or done.
- **Tools** (Logistics permission): sponsors, event-day steps, setup bundles, prize steps and sizes, equipment lists. A device type can be marked **Main Device** (names and leads a set, like a PC with its monitor and keyboard); devices follow the Type list's order everywhere. Prizes have a free-text **Type**.
- Cost: opening Logistics is one request; each edit's reply is applied on screen; an open event costs a few tiny reads every 20 seconds only while the tab is visible.
- Checks: `npm run test:logistics`, `test:logistics-plans`, `test:logistics-prizes`, `test:logistics-requests` (need a dev server).

## Notifications

`createNotifications` writes the bell and sends push together. Kinds people can mute (Profile → notifications): meetings, events, account, help and **docs** (`doc_required`, `doc_comment`). A kind not listed always sends.

## Scheduled jobs (`vercel.json`, `src/app/api/cron`)

The free Vercel plan allows two scheduled jobs, each at most once a day, so `vercel.json` has exactly two. Each one is a single route that runs its steps in turn (a failure in one never stops the next).

| Job | Steps | Code |
|---|---|---|
| `daily-reminders` | Day-before and hour-before event reminders; "Today at ..." meeting reminders; a nudge to people who haven't answered a meeting plan | `lib/notifications/eventReminders.ts`, `lib/meetings/reminders.ts`, `lib/meetings/meetingPlanServer.ts` |
| `daily-maintenance` | Removes old notifications (audit alerts after 14 days; ticket and meeting notices 14 days after they are read, 45 at most; everything else 30 read or 90 at most) and individual meeting reactions after 7 days; starts a new quarter's inactive markers; records the team roster and archives finished years; reminds staff of help tickets open over 2 days and tells the admins how many members joined in the last day; tells the admins when the database or file storage reaches 80% / 90% of the free plan (once a week per level; files are totalled on Sundays); on Sundays removes files nothing uses and shrinks old pictures | `lib/meetings/reactionCleanup.ts`, `lib/notifications/notificationCleanup.ts`, `lib/members/quarters.ts`, `lib/members/teamYears.ts`, `lib/storage/storageMaintenance.ts`, `lib/notifications/adminAlerts.ts` |

Both are called with `Authorization: Bearer $CRON_SECRET`. `daily-maintenance?only=notifications|quarters|teams|help|signups|usage|storage` runs a single step; on a dev machine `x-cron-dev: 1` may run only the quarters and teams steps. Don't add a third job to `vercel.json`; add a step to one of these two instead.


## Event check-ins page (Events)
An event's ticket list is its own page, **Events › the ticket count on an event's row** (`/portal/events/check-ins/<event slug>`, not a pop up): counts, a search box (name or gamer tag), **Sort** (Registered, Name, Checked-in time, Status, with an up/down arrow) and **Group** (None, Status, AS form for events that have it). Search, sort and group are in the address (`q`, `sort`, `dir`, `view`). People who can manage points get **Check In** (no scan) and **Undo** on each row. `EventCheckinsPage.tsx`; data from `GET /api/events/<slug or id>/checkins`.

## Event report (sponsors)
- **Where:** an event's summary page (`/portal/events/<id>/summary`, anyone with `checkin`). It is a formal, white-sheet report in Triton Gaming navy and gold. **Save as PDF** draws the PDF itself in the browser (no browser print dialog, so no address or page title in the margins): a one-page summary (key numbers, key findings, arrival and ticket-timing charts, audience and interest breakdowns, gender and pronouns always included) plus a second page with photos and the sponsor thank-you when there are any. Attendees' written comments are never included.
- **Details for each copy:** *Prepared for* (picked from the event's own sponsor list; the thank-you then names only that sponsor, otherwise all of them) and hand-typed *Social media reach* numbers, saved with the event in `events.report_social`.
- **Artwork:** the event's poster and design-guide stickers, and up to 6 photos from the gallery on its page.
- **Not in the PDF (team box under the report):** no-shows, cancelled tickets, points, paid tickets and revenue, check-in form completion and where ticket claims came from (QR scans show as Direct, so it understates).
- **Footnote:** data has been collected since the 2026-2027 school year (September 2026); profile details are optional in the portal, so those figures cover only attendees who shared them.

## Signing in

- **Sign-in service down:** the login page first checks that Supabase answers (8 s); if not it says "Can't reach the sign-in service right now. Please try again in a minute." instead of sitting on "Redirecting…".
- **Ended session in an open tab:** `components/portal/SessionGuard.tsx` (mounted in the portal layout) watches our own `/api/` calls; on a 401 it asks Supabase whether anyone is still signed in and, if not, sends the tab to `/login?next=<page>`. It asks at most every 30 s and redirects at most once a minute, so it can never loop.

## Logistics: the Prizing page

Two views, switched at the top and kept in the address (`/portal/logistics/<event>/prizing`, `/portal/logistics/stock/prizes`): **This Event** (the stations of one event, picked beside it; opens on today's or the next event) and **In Stock** (every prize). Both use the same collapsible blocks: a header (click anywhere on it) with totals, then rows. Everything starts folded; the **One at a time** switch (remembered on the device) makes opening one fold the others.
- **This Event:** **Group by** Station (default), Sponsor, Source, Size, Type or Status. Station blocks have the station's menu (rename, remove, **Lock / Unlock** when it came from a request, suggest prizes for what it asked); the other groupings list the same lines grouped by the prize, each line saying which station it is for. Every line has How many, Left and the event-day counters (all of them on a laptop; chips pick them on a phone). A later counter implies the earlier ones (3 given out means at least 3 sorted and picked up: lighter dashed marks, never red; Back To Storage implies nothing).
- **In Stock:** the prize blocks (grouped by Sponsor, Source, Size, Type or Status) with **In stock / Planned / Left** (left = on hand minus what open events promised). **Hide given out** (on by default) hides prizes with none on hand. The number on hand is changed right in the row.
- **Where a prize is from.** Every prize shows a labelled **From** line: the sponsor (or the club) and the event it was received for, as the event's address name (`division-showcase`). Click it (pencil) to change both from any view. `from_event` / `from_plan_id` remember the event (the name stays when the event is removed). In Stock offers **Fill in N missing events from past records** (a review list; the guess is the event the prize was first used at; `api/logistics/prizes/past-events`).
- **Where did they go?** Click a prize's Planned number (or its menu): how the count got here (added, changed by hand, given out), what each event did with it per station (promised, given out, back, still planned), and **Set the real count** (saved as a correction in the history with the difference). `api/logistics/prizes/<id>/breakdown`.
- **Free merch is counted loosely.** A prize size marked **Counted Loosely** (switch on the size in the settings gear; Tiny Prizing since 2026-10-25) has a level (Plenty / Some / Low / Out) instead of a number: a station simply has it, it is never over-promised, no counters beyond a tick, closing an event never takes it out of stock. `logistics_prizes.stock_level`, `logistics_options.meta.loose`.
- **Stations.** A station is a team's setup: its devices *and* its prizes. A station made only for prizes (a raffle, a hunt) is `prize_only` and stays off the Devices page until it has devices. Prize requests make a station with the size counts they asked for.
- **Event-day counters:** a tap adds one on the server, so two phones tapping both count; a typed number sets it. **All** in a block's header fills it. A **Given Out** count takes stock out as it is counted. **Closing** an event takes out what went out and was not counted back.
- **History.** Every prize has one (added, count changed, promised or taken off a station, given out, with who, when and why).
- **Working together.** Changes by other people appear within a second or two (Supabase Realtime on `logi-<event id>` and a stock channel). A pill floats in the bottom corner (`LivePill`): who else is here, what they are editing, and recent changes (hidden when you are alone).
- **Inputs never move the page.** Opening a number or text box over a row must not change the row's size or push anything (checked at 390, 820, 1180 and 1440 px by the layout-shift script).
- **The gear** holds this page's lists (sponsors, prize sizes and steps).

## Logistics: the tabs and an event's page

- Tabs: **Devices | Prizing | Events** (Events is last; Event Logistics opens on the Events list). **Events** is a list of cards (upcoming first, past ones folded) with numbers, a progress bar of devices filled, and **Open Devices / Open Prizing**. An event's page is an overview (teams, requests, devices, prizes; the last two open their tab) with folded parts: Device Requests, Prize Requests, Sponsor Loaners, Officer Loaners. Requests say who they are **For**. Allocation and the event day live only under Devices; prize stations under Prizing.


## Staffle

A raffle among staff for prizes from Prizing, under Team (`/portal/staffle`, one at `/portal/staffle/<name>`, the draw at `/portal/staffle/<name>/draw`). Everyone who can see Event Logistics can look and enter; the Event Logistics permission makes Staffles, runs the draw and marks prizes picked up.
- **A Staffle** has a name, who may enter, a pickup note and items (a prize and how many people win it). It is made first, with its **prizes picked afterwards** on its page (Pick Prizes / Change Prizes); it can't be opened until it has some. It is **opened and closed by hand** (Not Open Yet → Open ⇄ Closed → Drawn → Ended); no times. Until it is ended or removed its items are **held back from stock** (they count as Planned); a prize marked picked up leaves stock; ending (a drawn Staffle) or removing gives back what was not picked up. `staffles`, `staffle_items`, `staffle_entries`, `staffle_winners` (`passed_at` for a winner passed over).
- **Entering:** tick the prizes you want, one free entry each; the rules are checked as you enter (`lib/staffle/rules.ts`): chosen like a meeting's audience, without teams (the meetings `AudiencePicker`): roles ticked (Exec, Leads, Officers, Recruits) plus people picked by name; then **left out**: people with strikes, people with a warning, and anyone named (left out by name wins over everything). **Inactive members never enter**, not even by name; like a meeting, a role does not pull in alumni, a name does. You can enter many prizes but win only one per Staffle.
- **The draw** (`lib/staffle/draw.ts`, seeded so a reload shows the same result): prizes come up in random order, winners drop out of later prizes, a prize with N winners gives N different people. Staff press Draw on the **big screen** (full screen): a lottery drum of balls tumbles for each prize, then a ball drops out and opens on the winner's name, with confetti; Space, Enter or → goes on. Winners get a notification (and a push if on): "You won <prize> in <Staffle>!" with the pickup note. A drawn Staffle can be **drawn again** for a prize nobody picked up (one winner passed over, or all not picked up).
- **Picking up:** staff mark a winner "Picked Up" on the Staffle's page (takes one out of stock, history line, undo puts it back). **End** a drawn Staffle when pickup is over.
- **Pictures:** each prize has one picture (shrunk in the browser to a WebP of about 120 KB, bucket `prize-photos`), shown on the Prizing row and the Staffle card.
- Checks: `scripts/checks/staffle.mjs`, `lib/__tests__/staffle.test.ts`.

## Logistics: the event-day sheet (devices)

- **Skipped steps are not problems.** When a later step is ticked, earlier ones that were never ticked count as done: shown as a lighter check, counted in the totals and team progress, never red or orange, and never in the problems list. Tapping one ticks it for real. (`impliedDone` in `lib/logistics/plans.ts`.)
- **Parts are on the row.** A device's parts are small chips under its ID; tap one that is missing and it turns red. **Check done** is then one tap (no second dialog): it marks the step and saves the flagged parts as missing and the rest as present. After Check done, tapping a chip saves the change at once. A missing part is the red chip only on the event day (planning still warns).

## Refreshing the portal (and the installed app)

- An app added to the home screen has no reload, so the portal has its own: a **refresh button** in the desktop top bar (next to the theme switch; phones have none), a **pull down** at the top of a page (installed app only; phone browsers have their own) and, on a desktop, scrolling up once more at the top, and a **quiet refresh when the app is opened again after 90 seconds or more away** (never while a form has unsaved changes; the button and the pull ask first).
- All three call `refreshPortal()` (`lib/ui/refreshPortal.ts`). `PortalHub` then fetches the server's data again (`router.refresh()` inside a transition) and, once the answer is applied, rebuilds the open section, so what changed elsewhere (a check-in, an event, a device, someone's info) shows without leaving the page; the address, tab and page stay. Pull-down is `components/portal/PullToRefresh.tsx`, the button `PortalRefresh.tsx`.
- **The pull** works like a phone's own lists: the **whole page follows the finger down** (1:1 at first, then heavier, never past a limit) and a round bubble in the gap above fills a ring as you pull; at the point where letting go would refresh it turns yellow and ticks (phones that can vibrate). Let go early and the page springs back up; let go past it and the page waits part-way down while the bubble spins until it has its new data (at least a moment, so a fast answer never just blinks), then slides back. **On a desktop** (any browser) scrolling up once more at the very top does the same (a trackpad's two-finger swipe or the wheel, which moves the page half as far as a finger, so one notch is not enough), and it refreshes the moment it goes past the point of no return (a short pause before that springs it back). Only a scroll that begins at the top counts (a third of a second's pause starts a new one), so flicking up to the top and overshooting never refreshes by accident. While it refreshes the page stays put at the top (no scrolling either way, so nothing slides under the bubble), the bubble always stays above the page's top edge (it rises with the page when it slides back and never overlaps it), and the page waits a moment after the data arrives before sliding back. The page is moved with a `top` offset (`main[data-ptr-page]`, only while a pull is on), not a transform, so the bottom bar and dialogs stay where they are. Sideways swipes, upward scrolls, a list that is itself scrolled down, a dialog and a form field are never taken for a pull, and the page does not rubber-band under the bubble. The bubble is moved straight on the element (no re-render per touch move). The top-bar refresh button spins during any refresh, however it started. Reduced motion: no spin or bounce.

## Logistics: the Devices page

One page for every device and, with an event picked, where each one goes (`/portal/logistics/<event>/devices`). It opens on today's event (else the next one), and the event is switched at the top.
- **Planning | Event Day** switch (in the address; Event Day is where it opens on the event's own day). Planning shows the ID boxes that give each row its device; Event Day shows the step boxes, the parts chips and the ID bar. Both are the same sheet of stations.
- **Group by** Station, Type, Shelf, Status, Owner (club, sponsor loaners, officer loaners) or Games; the choice and "unfinished only" are in the address (`?view=type,open`). Loaners are rows in their station, marked Sponsor or Loaner. A station made only for prizes stays off this page until it has devices.
- **With no event** it is the stock: the table of every device (add, edit, shelf, tier, condition), with the same Group by.
- **The gear** holds this page's lists: device types, shelves, tiers, ports, games, kit parts, bundles and event steps (the old Tools tab is gone). Requests and the loaner lists stay under Events, one tap away from the event menu.
