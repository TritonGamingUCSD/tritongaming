# Roles and capabilities

_Generated by `npm run docs:roles` from `src/lib/portal/capabilities.ts` and `src/types/database.ts`. Do not edit by hand: change the code and run it again (add `-- --db` to compare with the live database)._

A **role** is a label on a person (someone can hold several, for example Officer and Division Lead). A **capability** is one thing that can be done. Every page and route asks `hasCapability()` whether the person may.

**Contents:** [At a glance](#at-a-glance) · [Portal sections](#portal-sections-by-role) · [Capabilities](#capabilities-by-role) · [Rules](#rules) · [What each capability allows](#what-each-capability-allows) · [Intended rules](#intended-rules-that-may-surprise-you) · [Database check](#database-check) · [Where each is checked](#appendix-where-each-capability-is-checked)

## At a glance

| Role | Who it is |
|---|---|
| **Guest** | Signed in with no role yet (for example a personal email that is not linked to UCSD). |
| **UCSD Student** | A verified UCSD student (given automatically for an @ucsd.edu sign-in). |
| **Recruit** | A prospective officer going through onboarding. Can see and take part in team things, but has no position yet. |
| **Alumni** | A former team member. Read-only: can open TG Members, Documentation, Events and Division Members. No check-in, no Rewards. |
| **Officer** | A team member. Can look at most things and staff check-in, but not create or edit events or docs. |
| **Division Lead** | Leads one or more divisions (a role scoped to a division). Edits only their own division’s page. |
| **Lead** | Runs a committee. Creates and edits events, docs and meetings they plan. |
| **Executive** | The executive board. Org-wide decisions: site content, points, rewards, strikes, quarters, every meeting. |
| **Admin** | Platform admin. Passes every capability check, and is the only role that can change roles or delete events. |
| **Inactive** | A marker next to Officer or Lead for a quarter they sit out. It removes the power to manage, host, delete, check in and scan (see Rules), and keeps everything that is only viewing. |

Admin passes every check. Roles combine: a person has everything each of their roles gives them.

## Rules

**How a check works**

1. Admin passes every check, whether or not Admin is listed for that capability.
2. Otherwise the person needs at least one role listed for it. Roles add up.
3. **Division Lead is scoped:** for division capabilities the check can name one division, and a Division Lead only qualifies for the division they lead.
4. **Inactive:** someone marked Inactive keeps every viewing permission but loses: `manage_events`, `delete_events`, `checkin`, `manage_site_content`, `manage_division`, `manage_divisions_directory`, `manage_roles`, `manage_docs`, `manage_rewards_shop`, `scan_redemptions`, `manage_points`, `manage_board_order`, `manage_meetings`, `manage_help`, `manage_strikes`, `manage_quarters`, `host_meetings`, `manage_logistics`, `host_trivia`. Meeting attendance and everything view-only stay. Admins are never affected.
5. **Granted permissions:** an admin can give one person or a group an extra permission (Admin → Access), added on top of their roles. Only these can be granted: `manage_strikes`, `manage_logistics`, `send_event_emails`, `view_attendance_reports`.
6. **Where it is enforced:** the capabilities marked “database” in the table below are also enforced by the database (row level security). The rest are enforced by the page or API route that uses them, so the route’s own check is the boundary.

**Other rules that are not capabilities**

- **Rewards are for UCSD students only.** Only someone whose **only** role is UCSD Student can earn points, claim rewards or be on the leaderboard. Any other role (or no role) rules it out. The database function `is_rewards_eligible()` and the app (`isRewardsEligible`) use the same rule, so no one else is awarded points. Their old points stay in the ledger, hidden. Exec and Admin keep a management-only Rewards section.
- **Team member (wide sense):** Exec, Lead, Officer, Recruit, Alumni or Admin. Used for team-wide views and to decide the desktop layout.
- **Verified member:** holds at least one role (even just UCSD). Decides UCSD-only event access and free ticket pricing.
- **Officer title on the profile:** only Officer, Lead and Exec can set it (a database trigger enforces this); Admin alone cannot. Lead and Exec must have one; Officers may add one.
- **Everyone signed in can** see their own profile, tickets, points, strikes and notifications, and ask for help. No capability is needed.

## Intended rules that may surprise you

These look unusual but were reviewed and confirmed as intended. Do not “fix” them without checking with the exec team.

- Check-In: Recruits, Officers and Leads can scan tickets, but checking someone in **by hand** or undoing a check-in needs “Change points”, which only Exec and Admin have.
- Rewards are student-only on purpose: a team member earns no points even if they check in to an event, and a guest with no role earns none either. Exec and Admin keep a management-only Rewards section.
- Alumni can open Events and an event’s check-in list (names and times), the same view Officers have. They still cannot check anyone in.
- Division Leads cannot open TG Members (`view_members` does not include them). They get Division Members and their own division’s page.
- Exec cannot open the Admin dashboard (`view_admin_dashboard` is Admin only), and only Admin can change roles or delete events.
- Only Exec and Admin can run **every** meeting. Leads can plan meetings but only manage their own.
- Anyone marked Inactive loses check-in, scanning and every `manage_`, `host_` and `delete_` capability, but keeps viewing and meeting attendance.
